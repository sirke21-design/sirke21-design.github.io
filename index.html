How I work

01

Real pain over abstract requirements.

I build for workflows I run myself. If I can't describe the friction in one sentence, I don't build for it.

02

Narrow bots, not general ones.

A bot scoped to one product line beats a general assistant on accuracy. Hallucination control is an architecture choice, not a prompt tweak.

03

User-permissioned, local-first.

Tools run on the user's own permissions and keep data local until export is explicit. No central data store without a clear reason.

04

Cross-check across models.

I triangulate outputs across Claude and ChatGPT before shipping. A single-model output is a first draft.

05

Ship to one user, then roll wider.

Power Platform lets me prototype in days. One CSM gets it first, I fix what breaks, then it goes to the team — pilot to production.

Meeting Assistant

A local-first Power Apps workbench that pulls the whole customer-meeting lifecycle — prep, execution, follow-up — into one workspace, with AI assistants grounded in JAGGAER's product knowledge.

~30%less pre/post-meeting manual work
5+tools replaced per CSM workflow
11screens, attachments handled across them
4product-specific bots: ASO · JA · JD · JI

The problem

CSMs lose hours every week jumping between Outlook, Teams, SharePoint, Jira and four product knowledge bases just to prepare for, run and follow up on one customer meeting. Context-switching lowers meeting quality and delays follow-up — both hit retention.

The solution

A workbench that runs on each CSM's own machine, pulls from their connected Microsoft tools, and uses purpose-built AI assistants — one per product line — to generate talking points, draft notes from transcripts and schedule follow-ups without leaving the app.

Design choices

Local-first

App data stays on each CSM's machine. Only meeting notes export to SharePoint, and only on explicit user action. No centralized telemetry.

Bot-per-product

Separate Copilot Studio bots for ASO, JA, JD and JI. A narrow scope per bot dramatically reduces hallucination compared with one general bot.

User-permissioned

Every connector runs under the user's own Microsoft credentials. The app never holds elevated permissions or reaches data the user can't already see.

Why it isn't just another meeting tool

Built by a CSM, not a developer.

The workflow logic comes from running customer meetings every day for years. Every screen exists because something specific was slowing me down.

Routed, not generic.

Most "AI assistants" use one general model and hope for the best. This one routes each question to a narrow, knowledge-grounded bot, so answers stay accurate inside each product's domain.

Local-first, user-permissioned.

No centralized data store and no scraping. The app uses the user's own Microsoft credentials and keeps everything local unless the user explicitly exports it.

Compounding knowledge base.

Every exported note becomes future bot context, so the assistant improves with use instead of going stale.
